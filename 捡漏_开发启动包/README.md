# 《捡漏》开发前置准备清单

> 目标：把「一份策划案」变成「CodeBuddy 能直接动手实现、且能自我验证的工程」。
> 本包内含：环境安装清单（第 8 节）、配置表 JSON（6 份）、项目上下文文件 `CODEBUDDY.md`、MVP 任务卡与验收标准。

---

## 0. 一句话结论

用 AI 写游戏，**成败不取决于 AI 会不会写代码，而取决于你有没有把设计变成「机器可读、可验证」的东西**。

所以前置准备的核心只有三件事：
1. **配置先于代码** —— 数值表先导出成 JSON，代码只读配置，不写死数字。
2. **逻辑先于画面** —— 核心逻辑写成纯 TypeScript（零引擎依赖），能跑单测。
3. **验收标准先于任务** —— 每张任务卡都带「跑什么命令、看什么结果算通过」。

这三条不做，后面会陷入「AI 改一处、坏三处、你也说不清哪错了」的死循环。

## 1. P0：动手前必须先定死的四件事

| # | 决策项 | 为什么必须现在定 | 我的建议（可推翻） |
|---|--------|------------------|--------------------|
| 1 | **技术栈** | 中途换栈 = 全部重写 | 见第 2 节 |
| 2 | **首发平台** | 决定打包、支付、审核、UI 尺寸 | 微信小游戏首发，后续补手游包 |
| 3 | **CodeBuddy 使用形态** | 决定你写什么上下文文件 | IDE 插件（写业务）+ CLI（跑脚本/单测） |
| 4 | **MVP 范围冻结** | 范围一膨胀，AI 也会失控 | 只做第 5 节的 8 张任务卡，其余一律不做 |

> ⚠️ 第 4 条最容易破功。图鉴、NPC 剧情、家园、排行榜、赛季——**在 MVP 验证「好玩」之前，一个都不要碰**。

## 2. 技术栈建议（附理由）

### 推荐组合

| 层 | 选型 | 理由 |
|----|------|------|
| 语言 | **TypeScript** | 类型即文档，AI 写 TS 的准确率明显高于动态语言 |
| 逻辑层 | **纯 TS 模块，零引擎依赖** | 能在 Node 里跑单测，是全项目最重要的资产 |
| 渲染层（阶段一） | **PixiJS + Vite** | 纯代码栈，浏览器里跑，AI 能完整读写、能自动化验证 |
| 渲染层（阶段二） | **Cocos Creator 3.8** | 微信小游戏生态最成熟，出包顺畅 |
| 单测 | **Vitest** | 快，配置少 |
| 配置校验 | **Zod** | 配置表写错时启动就报错，而不是上线才发现 |

### 为什么阶段一不直接用 Cocos Creator

Cocos 的场景（`.scene`）、预制体、动画大量依赖**编辑器里的鼠标操作**，这类资产 AI 读写起来很吃力、极易破坏。**纯代码栈里所有东西都是文本，AI 可以完整掌控。**

所以路径是：

```
阶段一：逻辑层（纯 TS） + 浏览器渲染（PixiJS）  →  验证核心循环好不好玩
阶段二：逻辑层原样搬进 Cocos Creator，只换渲染层  →  出微信小游戏
```

**前提条件**：逻辑层必须**严格不引用任何渲染 API**。这条用 ESLint 规则卡死（见第 3 节），否则第二阶段等于重写。

> 如果你确定只做 Cocos、不做 Web 原型，也可以——那就把「逻辑层纯 TS」这条要求执行得更严格，因为你会失去浏览器上的快速验证能力。

## 3. 推荐工程结构

```
pick-and-luck/
├─ CODEBUDDY.md            ← 项目上下文（本包提供，放到仓库根目录）
├─ .codebuddy/
│   └─ rules/              ← 分层规则（见第 4 节）
├─ design/                 ← 策划与数值（唯一数据源）
│   ├─ 捡漏_游戏策划案.html
│   └─ 捡漏_数值框架.xlsx
├─ config/                 ← 运行时配置（本包提供的 6 份 JSON）
├─ src/
│   ├─ core/               ← ★ 纯逻辑，禁止 import 任何渲染库
│   │   ├─ rng.ts          种子随机（可复现，调试救命）
│   │   ├─ economy.ts      售价结算、成长曲线
│   │   ├─ pickup.ts       拾取判定、稀有度 roll
│   │   ├─ gacha.ts        盲盒、保底、新手保护、重复转碎片
│   │   ├─ inventory.ts    背包格子与取舍
│   │   ├─ progression.ts  载具升级、区域解锁
│   │   └─ save.ts         存档序列化 / 迁移
│   ├─ config/
│   │   ├─ schema.ts       Zod 配置类型 + 校验
│   │   └─ loader.ts       加载 + 校验 + 冻结
│   ├─ render/             ← 渲染层（阶段一 PixiJS / 阶段二 Cocos）
│   ├─ scenes/             ← 各界面：拾取 / 垃圾场 / 盲盒货架 / 升级
│   ├─ ui/
│   └─ debug/              ← 调试面板（加钱、强制出货、跳区域）
├─ tests/core/             ← 单测，重点覆盖经济与概率不变量
└─ tools/                  ← 配置校验、数值回归脚本
```

**三条硬约束（写进规则文件，让 CodeBuddy 每次都遵守）：**
1. `src/core/` 下**禁止** `import` 任何渲染库、DOM API、平台 SDK。
2. `src/` 下**禁止**出现魔法数字——所有数值从 `config/` 读。
3. 所有随机必须走 `core/rng.ts`，禁止直接 `Math.random()`。

## 4. CodeBuddy 接入准备

CodeBuddy 的项目上下文机制（已在官方文档确认）：

| 文件 / 目录 | 作用 | 优先级 |
|------------|------|--------|
| `CODEBUDDY.md`（项目根目录） | 项目上下文，**全文默认加载** | 最高（存在时忽略 AGENTS.md） |
| `AGENTS.md`（项目根目录） | 同上的兼容写法 | 次之 |
| `.codebuddy/rules/*.md` | 结构化规则，可 `alwaysApply` 或按需加载 | 按规则生效 |
| `.codebuddy/agents/*.md` | 自定义子智能体（代码评审、架构师等） | 独立角色 |
| `openspec/` | SDD 规范驱动开发产物（`design.md` 等） | SDD 流程内 |

### 你需要做的

- [ ] 把本包的 `CODEBUDDY.md` 拷到游戏仓库**根目录**
- [ ] 在 `.codebuddy/rules/` 下建 3 条规则（建议）：
  - `core-purity.md` — `alwaysApply: true`，禁止 `core/` 引用渲染层
  - `no-magic-number.md` — `alwaysApply: true`，数值必须来自配置
  - `config-sync.md` — 按需加载，改数值必须同步 `design/` 与 `config/`
- [ ] 可选但强烈建议：用 CodeBuddy 的 SDD 流程把策划案转成技术规格
  （`/openspec:propose` → 生成 `openspec/xxx/design.md`），比口头描述稳定得多

> 规则控制在 500 行以内，只把 3–5 条核心规范设为 `alwaysApply`，其余按需加载。

## 5. MVP 任务卡（建议按序逐张交付）

> 每张卡都给了**可执行的验收标准**。让 CodeBuddy 一次只做一张，做完立刻验证。

### T1 · 工程骨架
初始化 Vite + TS + Vitest；建立第 3 节目录；配置 ESLint 分层约束。
**验收**：`npm run dev` 起服务、`npm run test` 全绿、`npm run build` 通过、故意在 `core/` 里 import PixiJS 时 ESLint 报错。

### T2 · 配置层
把 `config/` 下 6 份 JSON 加载进来，用 Zod 定义 schema 并校验、冻结。
**验收**：把 `zones.json` 里某区域的 `dropRates` 改成合计 0.99，启动时应**报错并明确指出是哪个区域**；正常配置下无警告。

### T3 · 核心逻辑（纯函数）
实现 `economy / pickup / inventory / progression`。
**验收**：单测覆盖——出售金额 = Σ(单价 × 品相系数 × 区域价格系数)；背包满时无法拾取多格物品；达到解锁等级才开放区域。

### T4 · 概率与开箱
实现 `gacha`：按概率 roll、保底计数、新手首抽保护、重复转碎片；随机走 `rng.ts`。
**验收**：
- 同一 seed 跑两次，产出序列**完全一致**
- 按盒概率采样 10000 次，**声明返还率**落在 **0.631 ± 0.02**；**含保底**的实测返还率另算，必须落在 0.55 – 0.65（当前 64.77%，解析解，见 `npm run check-config` 输出）
- 保底**按盒配置**：连续 `pityCounter` 次未出紫后下一抽必出紫（废品 150 / 家电 15 / 古董 10 / 记忆 15 / 限定 10），且**含保底实测返还率**仍须落在 0.55 – 0.65
- 新角色首次开箱稀有度 ≥ 蓝

### T5 · 拾取玩法
地图移动 + 点击拾取 + 稀有度反馈（音效/飘字/震动）+ 假点（空垃圾点）。
**验收**：产出分布符合当前区域 `dropRates`（跑 1000 次统计对比）；背包满时给出明确提示。

### T6 · 垃圾场结算
称重动画 + 金额结算 + 金币反馈。
**验收**：界面显示金额与 `core/economy` 的计算结果**完全一致**（同一函数出数，不允许前端另算）。

### T7 · 盲盒货架与开箱
货架陈列（M5 款）、**概率公示页**、开箱演出、图鉴点亮、重复转碎片提示。
**验收**：购买前可查看该盲盒完整概率；开完自动写入图鉴；重复藏品提示「已转为 X 碎片」。

### T8 · 升级商店 + 调试面板
载具升级、背包扩容；调试面板支持加钱/加体力/强制指定出货/跳区域。
**验收**：升级后格数立即生效；调试面板能一键复现「首抽必蓝」「第 10 抽保底」。

## 6. 埋点：第一天就要埋，不要等上线

策划案里的四个关键指标，**如果没有从第一天埋点，上线后你无法验证也来不及救**：

| 指标 | 埋点事件 | 目标值 |
|------|---------|--------|
| 单次会话时长 | `session_end` | 6–10 分钟 |
| 单次会话趟数 | `trip_complete` | ≥ 3 趟 |
| 首次开箱耗时 | `first_gacha_open` | ≤ 12 分钟 |
| 盲盒购买转化 | `gacha_shelf_enter` → `gacha_buy` | ≥ 60% |
| D1 留存 | `app_open`（按用户去重） | ≥ 35% |

MVP 阶段先用本地日志 + 调试面板看，**但事件名和结构现在就定死**，后面接分析平台不用返工。

## 7. 资产与合规

### 美术 / 音频（别等美术，先跑通）
- **一律先用占位**：纯色块 + 文字标签（如「塑料瓶」），别等素材。
- 只需准备一套「垃圾拟人化」的最小可辨认表情（圆眼 + 小嘴）即可验证手感。
- 字体：中文需确认商用授权（思源黑体等开源字体最稳）。

### 合规与账号（这部分建议尽早找法务 / 发行确认，不要自己拍）
- **微信小游戏**：需主体资质与 AppID；涉及虚拟支付需相应支付资质。
- **国内上线运营**：需要版号 / 备案，规则以最新政策为准 → **请向法务或发行确认**。
- **抽卡概率公示**：购买前必须可查（已在 T7 验收标准里）。
- **未成年人保护**：实名认证 + 消费限额，属上线硬门槛。
- **隐私政策 / 用户协议**：收集任何设备信息前必须具备。

## 8. 环境安装清单：装什么 / 暂时别装什么

> 原则：**只装当前阶段跑得起来的工具**。工具链每多装一层，你就会多花一天在配环境上，而不是在做游戏。

### 8.1 阶段一必装（第一天就要）

| 工具 | 用途 | 说明 |
|------|------|------|
| **Node.js LTS（≥ 20）** | 跑 Vite / Vitest | 本机已有 22.22.2，可直接用 |
| **pnpm** | 包管理 | Node 自带 corepack，`corepack enable pnpm` 即可 |
| **Git** | 版本控制 | `design/` 与 `config/` 都要进仓 |
| **VS Code 或 CodeBuddy IDE** | 写代码 | 配 ESLint 分层规则 |
| **Chrome / Edge** | 阶段一就在浏览器里跑 | DevTools 是你的主要调试手段 |
| **CodeBuddy（IDE 插件 + CLI）** | 写业务逻辑 + 跑脚本/单测 | 见第 5 节 |

**就这些。** 阶段一全是纯文本工程，不需要任何原生工具链。

### 8.2 阶段二再装（等核心循环验证「好玩」之后）

| 工具 | 用途 | 何时装 |
|------|------|--------|
| **Cocos Creator 3.8 + Cocos Dashboard** | 出微信小游戏包 | 阶段一的玩法验证通过后 |
| **微信开发者工具** | 预览小游戏、真机调试、上传代码包 | 同上，需先申请小游戏 AppID |

> 微信开发者工具和 Cocos 都是几个 GB 级别的安装，**在阶段一装它们只会分散你的注意力**。

### 8.3 ★ 先别装：Android Studio

| 工具 | 真实触发条件 | 为什么现在别装 |
|------|-------------|----------------|
| **Android Studio + Android SDK / NDK + JDK** | 只有当你要**打出 `.apk` / `.aab` 并上架安卓应用市场**时才需要 | ① 连 SDK、模拟器一起装掉 **10–15 GB**；② 它默认装的 SDK / NDK 版本**常常和 Cocos 要求的版本对不上**，装早了还得卸了重装；③ 装完你会忍不住去调环境，而不是做游戏 |

**明确不需要 Android Studio 的场景：**

- **微信小游戏 / 抖音小游戏**——运行环境由平台自己托管，走的是 JS 运行时 + 平台自己的开发者工具。**Android 和 iOS 都由平台覆盖，你一套代码天然双端。**
- **iOS 原生包**——那个需要的是 **macOS + Xcode**，不是 Android Studio。你在 Windows 上做不了，所以「手机原生双端」这个目标如果要走，iOS 侧要么用 Mac，要么外包。**这也是我建议首发出微信小游戏的原因之一。**

**什么时候你才真的必须装它：**
```
微信小游戏验证成功 → 决定出安卓原生包 → 需要上架华为/小米/OPPO 等应用市场 → 这时才装
```
触发条件非常明确，不用提前准备。

> 另外：**不要装 Android 模拟器**。真机 + 浏览器足够，模拟器吃内存还慢。

## 10. 五个常见坑（提前避开）

1. **把设计数字写死在代码里** → 后期调平衡要改几十个文件。**配置先行**。
2. **逻辑和渲染混在一起** → 想换引擎/出小游戏包时等于重写。**`core/` 保持纯净**。
3. **用 `Math.random()`** → 线上出了数值 bug 无法复现。**全部走种子随机**。
4. **一次让 AI 做太多** → 改一处坏三处。**一张任务卡一次交付，做完就验证**。
5. **先做图鉴/剧情/排行榜** → MVP 的「好玩」还没验证就堆系统，最后一定烂尾。**先冻结范围**。
